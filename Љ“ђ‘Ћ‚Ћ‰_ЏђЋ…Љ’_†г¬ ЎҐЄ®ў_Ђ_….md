ВВЕДЕНИЕ
Организация современных научно-практических конференций, форумов, образовательных семинаров, хакатонов и корпоративных выставок неразрывно связана с необходимостью обеспечения быстрого, безопасного и прозрачного контроля доступа посетителей. В условиях динамичного развития цифровой экосистемы Казахстана и перехода образовательных и деловых институтов к безбумажным технологиям традиционные способы учёта гостей — сверка с распечатанными списками на бумажных носителях, ручной поиск фамилий в таблицах или отметки карандашом на контрольно-пропускных пунктах — демонстрируют критическую неэффективность. Ручной учёт неизбежно приводит к формированию очередей на стойках аккредитации, путанице при наличии однофамильцев, человеческим ошибкам персонала, риску несанкционированного прохода посторонних лиц и полному отсутствию оперативной аналитики для организаторов в режиме реального времени.

Актуальность темы обусловлена необходимостью автоматизации контрольно-пропускных процессов и учёта посещаемости участников массовых мероприятий посредством внедрения мобильных клиент-серверных технологий и персональной оптической идентификации на базе двумерных штрихкодов (QR-кодов). Смартфон сегодня является неотъемлемым персональным устройством как для участника события, так и для организатора или волонтёра. Использование персонального цифрового QR-билета на экране мобильного устройства исключает необходимость печати бейджей и бумажных билетов, снижая материальные издержки и экологическую нагрузку, а применение встроенной камеры смартфона в качестве высокоскоростного аппаратного считывателя превращает мобильное устройство организатора в полноценный терминал регистрации без закупки дорогостоящего специализированного оборудования.

Целью курсового проекта является проектирование и разработка кроссплатформенной мобильной системы регистрации участников конференций и мероприятий по QR-коду на базе фреймворка Flutter и облачной инфраструктуры Google Firebase, обеспечивающей мгновенную бесконтактную валидацию билетов, защиту от повторного прохода и мониторинг посещаемости в реальном времени.

Для достижения поставленной цели в работе сформулированы и решены следующие задачи:
1. Провести детальный теоретический анализ предметной области мобильных систем контроля доступа и регистрации участников, изучить стандарты двумерного штрихкодирования и выполнить аналитический обзор существующих отечественных и мировых программных аналогов.
2. Обосновать выбор технологического стека, инструментов разработки, клиентского фреймворка и облачной серверной платформы для хранения данных в реальном времени.
3. Спроектировать многослойную архитектуру программного продукта, структуру NoSQL базы данных Cloud Firestore, формат защищённого полезного содержимого QR-билета и математико-логический алгоритм валидации чек-ина (Check-in) с защитой от коллизий и повторных проходов.
4. Разработать клиентскую часть мобильного приложения на языке Dart с использованием фреймворка Flutter, включающую экран-заставку (Splash Screen), модули аутентификации и регистрации, адаптивную навигацию, дашборд с аналитическими счётчиками, каталог мероприятий, модуль генерации динамических QR-билетов, встроенный модуль оптического сканирования через камеру, форму создания и редактирования событий, а также профиль пользователя с разграничением ролевого доступа.
5. Интегрировать клиентское приложение с облачными сервисами Firebase Authentication и Cloud Firestore, реализовать потоковую синхронизацию данных в реальном времени и атомарные транзакции изменения числа зарегистрированных мест.
6. Разработать и провести комплексную программу тестирования системы, включающую модульные тесты валидаторов и моделей данных, статический анализ исходного кода, функциональное тестирование сквозных пользовательских сценариев и верификацию правил безопасности.

Объектом исследования выступает процесс регистрации, контроля доступа и координации потоков участников на научно-образовательных, деловых и культурно-массовых мероприятиях.

Предметом исследования являются методы, программные средства, архитектурные шаблоны и алгоритмы создания кроссплатформенных мобильных приложений регистрации участников на базе двумерных QR-кодов и облачных баз данных реального времени.

Целевая аудитория разработанного программного решения строго разделена на две ключевые ролевые категории:
1. Организаторы и персонал мероприятий (администраторы, координаторы площадок, волонтёры на стойках регистрации) — используют мобильное приложение для оперативного создания событий, управления квотами мест, высокоскоростного оптического сканирования персональных QR-кодов гостей через камеру мобильного устройства, мгновенной проверки подлинности билетов, ручной корректировки списков и непрерывного отслеживания аналитики фактической явки гостей в режиме реального времени.
2. Участники мероприятий (делегаты, гости, спикеры, студенты, слушатели) — используют приложение для ознакомления с каталогом актуальных событий, поиска и фильтрации конференций по направлениям, прохождения мгновенной цифровой регистрации, просмотра персональных сведений в профиле и предъявления уникального электронного QR-билета при прохождении контрольного пункта.

Основной функционал приложения включает:
- экран-заставку с анимированным логотипом и фоновой проверкой сессионного состояния пользователя;
- регистрацию новых пользователей с клиентской и серверной валидацией входных параметров (email, надёжность пароля, имя, контактные данные, выбор роли);
- авторизацию пользователей с обработкой ошибок некорректных учётных записей и сохранением сессии;
- ролевую модель разграничения прав доступа (организатор / участник);
- главную страницу (дашборд) со сводной статистикой посещаемости и быстрыми действиями в зависимости от активной роли;
- единую систему навигации на базе современного Material 3 NavigationBar;
- каталог мероприятий с поисковой индексацией «на лету», фильтрацией по категориям (конференция, семинар, хакатон, воркшоп, митап) и сокрытием прошедших событий;
- полный цикл CRUD-операций над мероприятиями (создание, чтение, редактирование параметров, каскадное удаление);
- механизм регистрации на мероприятие с гарантией отсутствия дубликатов билетов и атомарным контролем свободных мест через транзакции Firestore;
- модуль визуализации электронного билета с векторной генерацией QR-кода на базе уникального UID-хэша и 6-значного резервного криптостойкого буквенно-цифрового кода;
- высокопроизводительный встроенный сканер QR-кодов на базе системных библиотек камеры с аппаратным распознаванием, защитой от дребезга (debounce) и цветовой индикацией результатов верификации (успешный проход, повторная попытка, чужое мероприятие, недействительный билет);
- раздел профиля с отображением реквизитов пользователя, возможностью редактирования личных данных и функцией защищённого выхода из учётной записи (Logout).

Практическая значимость работы заключается в создании готового к практической эксплуатации программного комплекса, который может быть внедрён для обслуживания внутренних и открытых мероприятий Колледжа ТОО «Astana IT University», а также сторонних академических и коммерческих форумов. Применение системы позволяет сократить среднее время прохождения одного участника через пункт контроля с 45–60 секунд (при бумажном учёте) до 1,5–2 секунд при оптическом сканировании, полностью исключить финансовые расходы на печать бумажных билетов и предоставить руководству оргкомитета исчерпывающую объективную статистику явки гостей непосредственно во время проведения события.

ГЛАВА 1. ТЕОРЕТИЧЕСКАЯ ЧАСТЬ
1.1 Общие понятия мобильных систем регистрации и контроля посещаемости мероприятий
Мобильная информационная система контроля посещаемости и регистрации участников представляет собой специализированный программно-аппаратный комплекс, функционирующий на портативных смартфонах и планшетах, ориентированный на автоматизацию сбора, обработки, верификации и визуализации данных о посетителях массовых мероприятий. Ключевая специфика таких систем заключается в объединении двух разнородных сценариев взаимодействия: сценария потребителя услуг (участника), требующего минималистичного интерфейса для получения пропуска, и сценария оператора (организатора), которому необходим высокоточный инструмент считывания идентификаторов в условиях интенсивного входящего потока людей.

Фундаментальным компонентом современных систем бесконтактного чек-ина является оптическое распознавание двумерных матричных кодов (QR-кодов — Quick Response Code) [1]. Разработанный в 1994 году стандарт QR-кода (ISO/IEC 18004) обеспечивает возможность кодирования буквенно-цифровой информации объёмом до нескольких килобайт с поддержкой избыточности по алгоритму Рида — Соломона [2]. Применение алгоритмов коррекции ошибок позволяет стабильно декодировать оптический код даже при физическом повреждении, загрязнении или считывании с экранов смартфонов при низкой яркости подсветки и неблагоприятных углах наклона камеры.

В архитектурном плане мобильные приложения подразделяются на четыре основные категории:
1. Нативные приложения (Native) — разрабатываемые индивидуально под конкретную операционную систему (Kotlin/Java для ОС Android, Swift/Objective-C для iOS). Обладают максимальной производительностью и прямым доступом к аппаратному обеспечению, однако требуют двукратных трудозатрат на сопровождение двух независимых кодовых баз.
2. Мобильные веб-приложения (Web/PWA) — функционирующие внутри браузера. Характеризуются простотой распространения, но имеют существенные ограничения при работе с аппаратными интерфейсами камеры (Camera2 API/AVFoundation), что критично для скорости сканирования QR-кодов.
3. Гибридные приложения (Hybrid) — оболочки WebView (Apache Cordova, Ionic), транслирующие HTML/JS код. Зачастую демонстрируют заметные задержки интерфейса и низкую частоту кадров (FPS) при рендеринге динамических списков.
4. Кроссплатформенные компилируемые приложения (Flutter, React Native) — программные системы, исходный код которых пишется на едином языке программирования и компилируется непосредственно в машинный код целевого процессора (ARM64/x86_64).

Для задачи построения системы регистрации выбор компилируемого кроссплатформенного фреймворка Flutter является наиболее обоснованным. Он гарантирует прямой доступ к видеопотоку камеры устройства без посредников, обеспечивает стабильную отрисовку интерфейса со скоростью 60–120 кадров в секунду и позволяет разворачивать клиентское приложение на платформах Android, iOS и в веб-браузерах без переписывания бизнес-логики.

Особое внимание в мобильных системах регистрации уделяется организации серверной инфраструктуры и хранению данных. В отличие от традиционных информационных систем, где преобладают периодические запросы чтения, система контроля мероприятий характеризуется выраженными пиковыми нагрузками в момент открытия дверей (check-in rush). Сотни участников одновременно обращаются к серверу для скачивания билета, а десятки организаторов непрерывно отправляют запросы на подтверждение статуса прохода. В таких условиях реляционные СУБД с жесткими блокировками таблиц могут демонстрировать повышенное время отклика. Напротив, облачные бессерверные (Serverless) платформы реального времени, такие как Google Cloud Firestore, построенные на концепции документно-ориентированных NoSQL баз данных с распределённой репликацией и WebSocket-соединениями (Data Streams), позволяют мгновенно распространять сведения о факте прохода гостя на все подключённые устройства волонтёров [3].

При обработке сведений об участниках (фамилия, имя, адрес электронной почты, контактный телефон, организация) мобильное приложение обязано неукоснительно соблюдать нормы законодательства Республики Казахстан, в частности Закон РК от 21 мая 2013 года № 94-V «О персональных данных и их защите» [15]. Это требует обязательного шифрования сетевого трафика по протоколу TLS 1.3, надёжного хеширования аутентификационных данных, изоляции прав доступа через политики безопасности и хранения только минимально необходимого объёма пользовательской информации.
1.2 Обзор существующих программных решений
Для формулирования функциональных и технико-эксплуатационных требований к разрабатываемой системе был проведён детальный сравнительный анализ представленных на международном и казахстанском рынках коммерческих и открытых платформ регистрации и контроля билетов.

1. Eventbrite (Eventbrite Organiser) — мировой лидер в области продажи билетов и регистрации на мероприятия. Предоставляет развитое мобильное приложение для организаторов с функцией считывания штрихкодов встроенной камерой. Главными недостатками системы являются полная коммерческая закрытость, высокая комиссия за обработку транзакций, невозможность локального развёртывания в инфраструктуре казахстанских учебных заведений, блокировка ряда платёжных шлюзов и перегруженность интерфейса маркетинговыми инструментами, избыточными для академических и локальных событий.
2. Timepad (Timepad Чекер) — популярная платформа электронного билетирования на территории СНГ. Приложение для сканирования поддерживает работу со списками участников, однако требует создания платного аккаунта организатора для доступа к полному функционалу сканера, имеет жёсткую привязку к внутренней экосистеме сервиса и периодически испытывает задержки синхронизации статусов между устройствами волонтёров при нестабильном интернет-соединении.
3. Google Формы в связке с Google Таблицами — наиболее часто используемое «кустарное» бесплатное решение в студенческой среде. Организаторы создают веб-опросник, собирают список участников в таблицу и при входе вручную ищут посетителей поиском по тексту. Решение не содержит встроенного механизма генерации и валидации QR-кодов, не исключает повторный проход по скопированной ссылке, чрезвычайно медлительно (поиск человека занимает более 30–60 секунд) и полностью непригодно для мероприятий с аудиторией свыше 50 человек.
4. Meetup — специализированный сервис для организации встреч профессиональных сообществ и митапов. Ориентирован на формирование социальных групп по интересам, однако механизмы экспресс-валидации участников на входе развиты слабо: подтверждение присутствия носит заявительный характер, отсутствует наглядный экран специализированного билетного QR-кода с защитой от повторного прохода.

2.1 Разработка архитектуры приложения
Программный комплекс спроектирован в соответствии с принципами чистой многослойной архитектуры (Clean Layered Architecture) с разделением исходного кода на слабосвязанные модули [2, 3]. Вся структура проекта в каталоге `lib/` организована по функционально-слоевому принципу:
- `lib/core/` — общие конфигурационные элементы приложения: палитра стилей и тема Material 3 (`theme.dart`), системные утилиты валидации и форматирования дат (`utils.dart`);
- `lib/models/` — доменные модели сущностей предметной области (`models.dart`);
- `lib/services/` — слой управления глобальным состоянием и бизнес-логикой взаимодействия с облачной инфраструктурой (`app_state.dart`);
- `lib/screens/` — экраны пользовательского интерфейса (Presentation Layer);
- `lib/widgets/` — переиспользуемые составные компоненты интерфейса (`common.dart`).

Слой представления (Presentation Layer) построен исключительно на декларативных виджетах Flutter. Виджеты являются «тонкими» компонентами: они не содержат прямой логики обращения к базе данных или генерации сетевых пакетов, а лишь транслируют действия пользователя в вызовы соответствующих методов контроллера `appState` и подписываются на его уведомления с помощью виджетов `ListenableBuilder`.

Слой предметной области и состояния (Domain & Service Layer) инкапсулирован в классе `AppState`, наследующем базовый класс `ChangeNotifier`. Он выполняет следующие функции:
- отслеживание текущей сессии через поток `FirebaseAuth.instance.authStateChanges()`;
- хранение активного профиля пользователя `AppUser` и проверка ролей (`isOrganizer`, `isLoggedIn`);
- подписка на потоковые обновления коллекций Firestore: поток `_eventsSub` непрерывно считывает изменения каталога мероприятий, а поток `_regsSub` отслеживает выданные билеты (для организатора — билеты на его события, для участника — только его персональные билеты);
- кэширование актуального среза данных в оперативной памяти мобильного устройства для исключения задержек интерфейса при пролистывании списков;
- оповещение интерфейса об изменениях данных посредством вызова `notifyListeners()`.

Слой облачных сервисов (Data Layer) обеспечивает персистентное хранение данных и синхронизацию. Прямое взаимодействие с Firebase SDK гарантирует автоматическое шифрование канала передачи данных и обработку сетевых ошибок на уровне клиента.

2.3 Проектирование структуры базы данных
В качестве хранилища данных программного комплекса выбрана NoSQL СУБД Google Cloud Firestore. В отличие от табличных баз данных, Firestore хранит информацию в виде коллекций, содержащих документы с гибким набором полей ключ-значение.

Схема базы данных включает три основные коллекции высшего уровня:

2.4 Проектирование протокола взаимодействия, формата QR-кода и безопасности
Для обеспечения надёжной и защищённой работы оптического сканера был разработан специализированный протокол сериализации данных электронного билета.

Формат полезной нагрузки QR-кода (QR Payload). Вместо передачи сырых пользовательских данных (что противоречило бы требованиям защиты персональной информации) или огромных JSON-строк (затрудняющих оптическое распознавание камерой с дальнего расстояния) был спроектирован компактный конкатенированный строковый формат с префиксом протокола и разделителями:
```
QRREG|<registrationId>|<code>
```
где:
- `QRREG` — статический служебный префикс (Magic Header), позволяющий камере мгновенно отсекать сторонние штрихкоды, случайно попавшие в объектив (например, QR-коды платежей Kaspi или инвентарные номера мебели);
- `registrationId` — уникальный составной идентификатор билета вида `<eventId>_<userId>`;
- `code` — криптографически стойкий 6-значный буквенно-цифровой проверочный код.

Пример полезной нагрузки:
```
QRREG|eA89zL01k_uV55Rt89p|H8J4M2
```

Алгоритм генерации резервного 6-значного кода. Для ситуаций, когда камера участника повреждена, дисплей разбит либо физически отсутствует возможность сканирования, система генерирует резервный проверочный код из безопасного алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, из которого намеренно исключены визуально схожие символы (`0` и `O`, `1` и `I`). Генерация выполняется с помощью системного генератора псевдослучайных чисел `Random.secure()`:
```dart
String _newCode() {
  const alphabet = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789';
  final r = Random.secure();
  return List.generate(6, (_) => alphabet[r.nextInt(alphabet.length)]).join();
}
```

Политика безопасности и правила доступа Cloud Firestore Security Rules. Защита базы данных от несанкционированного изменения обеспечивается серверными правилами Firebase Security Rules:
- Чтение коллекции `events` разрешено всем аутентифицированным пользователям.
- Создание, модификация и удаление документов в `events` разрешены только пользователям с ролью `organizer`.
- Документы в коллекции `registrations` могут создаваться участником только для самого себя (`request.auth.uid == request.resource.data.userId`).
- Поле `checkedInAt` в документе регистрации может модифицироваться исключительно организатором события (`request.auth.uid == resource.data.organizerId`).
2.5 Алгоритм генерации и валидации QR-билетов и предотвращения повторного прохода
Ключевой задачей системы является строгое предотвращение повторного прохода (Anti-Passback) по одному и тому же билету (например, если участник сфотографировал экран и переслал QR-код другу через мессенджер).

Математико-логическая модель валидации билета описывается конечным автоматом состояний. Пусть $R$ — объект регистрации, $QR_{raw}$ — распознанная камерой строка, $E_{active}$ — выбранное на сканере мероприятие.
1. Распознавание и декомпозиция строки:
$$QR_{raw} \xrightarrow{split('|')} \{Header, ID_{reg}, Code\}$$
Если $Header \neq 'QRREG'$, выполняется проверка резервного 6-значного кода.
2. Поиск билета в активном реестре:
$$R = find(ID_{reg}) \lor find(Code)$$
Если билет не найден: статус $\rightarrow \mathbf{notFound}$.
3. Проверка соответствия мероприятию (если организатор установил локальный фильтр по залу/секции):
$$R.eventId \neq E_{active} \implies \text{статус} \rightarrow \mathbf{wrongEvent}$$
4. Проверка первичного прохода:
$$\text{Если } R.checkedInAt \neq \mathbf{null} \implies \text{статус} \rightarrow \mathbf{already} \text{ (ОТКАЗ: ПОВТОРНЫЙ ПРОХОД)}$$
5. Фиксация входа:
$$R.checkedInAt \leftarrow Timestamp_{now}, \quad \text{статус} \rightarrow \mathbf{ok} \text{ (ПРОХОД РАЗРЕШЕН)}$$

Атомарность резервирования мест на мероприятии (`runTransaction`). При записи участника на событие критически важно исключить состояние гонки (Race Condition), когда на последнее оставшееся свободное место одновременно претендуют два пользователя. Для решения этой проблемы в методе `registerForEvent` реализована распределённая транзакция Firestore:
```dart
await _db.runTransaction((tx) async {
  final ev = await tx.get(evRef);
  final data = ev.data()!;
  final capacity = (data['capacity'] as num).toInt();
  final taken = ((data['registered'] ?? 0) as num).toInt();
  if (taken >= capacity) throw Exception('Свободных мест нет');
  tx.set(regRef, newRegistration.toJson());
  tx.update(evRef, {'registered': FieldValue.increment(1)});
});
```
Транзакция гарантирует, что инкремент счетчика зарегистрированных лиц и создание билета выполняются как единая неделимая операция.

3.5 Модуль регистрации на мероприятия и электронного билета с QR-кодом

3.6 Поиск, фильтрация и категоризация мероприятий
Для удобной навигации в условиях большого количества событий в каталоге `EventsScreen` реализован развитый комплекс поисково-фильтрационных инструментов:

3.7 Модуль сканирования QR-кодов и фиксации чек-ина участников
Модуль сканирования является ключевым функциональным ядром системы и реализован в файле `lib/screens/scanner_screen.dart` (рисунок 11). Экран доступен пользователям с ролью «Организатор» и оптимизирован для работы в условиях плотного потока людей на проходных.

В верхней части экрана размещен селектор мероприятия: организатор может выбрать режим «Все мои мероприятия» либо жестко зафиксировать конкретное событие (например, секцию «Конференция AI»), исключая ошибочный пропуск гостей с параллельных потоков.

В центре экрана расположена область оптического захвата на базе контроллера `MobileScannerController` библиотеки `mobile_scanner`. Распознавание штрихкодов выполняется аппаратно на уровне графического процессора с частотой кадров видоискателя камеры (до 60 кадров в секунду). В коде реализована аппаратная фильтрация дубликатов `DetectionSpeed.noDuplicates`.

Для исключения ложных повторных срабатываний при удержании одного билета перед объективом внедрен программный механизм защиты от дребезга (debounce):
```dart
Future<void> _process(String raw) async {
  final now = DateTime.now();
  if (_busy || (raw == _lastRaw && now.difference(_lastAt).inSeconds < 3)) return;
  _busy = true;
  _lastRaw = raw;
  _lastAt = now;
  final res = await appState.checkIn(raw, onlyEventId: _eventFilter);
  if (!mounted) return;
  setState(() => _result = res);
  _busy = false;
}
```

Под окном видоискателя выводится крупная интерактивная карточка результата сканирования с цветовой индикацией:
- Зеленый цвет (Статус OK): «Вход разрешён! Участник успешно зарегистрирован» с выводом ФИО гостя и названия события;
- Красный/Оранжевый цвет (Статус ALREADY): «Внимание! Билет уже был использован ранее в ЧЧ:ММ!» — срабатывает защита от повторного прохода;
- Желтый цвет (Статус WRONG_EVENT): «Билет от другого мероприятия!»;
- Серый цвет (Статус NOT_FOUND): «Билет не найден в базе данных».

Ниже камеры размещено поле резервного ручного ввода 6-значного буквенного кода с кнопкой «Проверить код», что гарантирует бесперебойность работы контрольного пункта даже при повреждении камеры или разбитом экране участника.

```dart
Future<CheckInResult> checkIn(String raw, {String? onlyEventId}) async {
  final input = raw.trim();
  Registration? found;
  final parts = input.split('|');
  for (final r in _regs) {
    if (parts.length == 3 && parts[0] == 'QRREG') {
      if (r.id == parts[1] && r.code == parts[2]) found = r;
    } else if (r.code == input.toUpperCase()) {
      found = r;
    }
  }
  if (found == null) return const CheckInResult(CheckInStatus.notFound);
  final reg = found;
  final event = eventById(reg.eventId);

  if (onlyEventId != null && onlyEventId != reg.eventId) {
    return CheckInResult(CheckInStatus.wrongEvent, registration: reg, event: event);
  }
  if (reg.checkedIn) {
    return CheckInResult(CheckInStatus.already, registration: reg, event: event);
  }
  final now = DateTime.now();
  final err = await _guard(() => _db
      .collection('registrations')
      .doc(reg.id)
      .update({'checkedInAt': now.millisecondsSinceEpoch}));
  if (err != null) return CheckInResult(CheckInStatus.error, message: err);
  return CheckInResult(CheckInStatus.ok, registration: reg.withCheckIn(now), event: event);
}
```

2. Атомарная транзакция записи на мероприятие с контролем мест (`lib/services/app_state.dart`):
```dart
Future<String?> registerForEvent(String eventId) async {
  final user = _profile;
  if (user == null) return 'Войдите в аккаунт';
  final evRef = _db.collection('events').doc(eventId);
  final regRef = _db.collection('registrations').doc('${eventId}_${user.id}');
  String? problem;
  final err = await _guard(() async {
    await _db.runTransaction((tx) async {
      final ev = await tx.get(evRef);
      if (!ev.exists) { problem = 'Мероприятие не найдено'; return; }
      final existing = await tx.get(regRef);
      if (existing.exists) { problem = 'Вы уже зарегистрированы'; return; }
      final data = ev.data()!;
      final capacity = (data['capacity'] as num).toInt();
      final taken = ((data['registered'] ?? 0) as num).toInt();
      if (taken >= capacity) { problem = 'Свободных мест нет'; return; }
      tx.set(
        regRef,
        Registration(
          id: regRef.id,
          eventId: eventId,
          userId: user.id,
          userName: user.name,
          userEmail: user.email,
          organizerId: (data['organizerId'] ?? '') as String,
          code: _newCode(),
          createdAt: DateTime.now(),
        ).toJson(),
      );
      tx.update(evRef, {'registered': FieldValue.increment(1)});
    });
  });
  return err ?? problem;
}
```
